## 工作流建设定位

P-001同时是当前代码统一与重构问题，也是工作流系统的第一个高复杂度真实验证实例，但两种责任不能互相替代：

- P-001工程责任：完成RV1126B（历史别名RV1126BP）与HiSilicon DMS及其直接依赖的审计、统一、重构、实现和外部验证；
- 工作流验证责任：验证人的大量经验信息能否转化为证据任务、设计约束、人工决定、验收条件和稳定知识；
- 领域复用责任：从P-001提取算法工程可复用的节点类型和制品契约，并通过第二个独立算法问题验证；
- 通用化责任：领域复用成立后，再把引擎、领域模板和项目实例解耦，形成独立通用公开库。

演进顺序为：

```text
P-001真实设计与验证 → 算法工程可复用工作流 → 通用公开库
```

后两级不是当前基线验证节点的完成条件，也不能代替P-001的代码和板端验收。

## 继承的核查结论

以下内容来自 `docs/` 下既有 DMS 统一核查文档，当前只作为后续审计输入；进入设计或实现前必须重新绑定到当前固定提交、构建、模型、配置和运行证据。

### 范围与兼容

- 统一目标是合并内部 DMS 业务核心，不是直接用一套新公共头替换两端外部接口。
- Hi3519DV500 和 RV1126B 的原 API、ABI、库名、依赖、配置格式、模型路径、初始化/送帧/回调/释放时序都要分别建立兼容基线。
- `SetSourceData` 是疑似废弃/待退役兼容入口；删除前必须完成调用者、导出符号、上层应用和替代入口证据。
- PC 可用于公共业务逻辑快速回归，但不能替代板端媒体帧、零拷贝、缓存、SDK 生命周期和性能验证。

### 架构方向

- 候选结构是“公共 DMS 核心 + Hi/RV/PC 平台后端 + Hi/RV 外部兼容层 + 较薄公共基础能力层”。
- 公共业务核心可以承载状态、ROI、阈值、后处理、结果合并和告警规则，但不得直接依赖平台 SDK。
- 平台后端承载帧映射、颜色转换、缩放、模型加载、推理执行、缓存同步和芯片资源生命周期。
- 公共基础能力只有在 DMS 真实调用、无 DMS 业务规则、可独立构建/测试/发布时才能进入 `src/base`。
- 前处理应作为候选公共能力审计：算法业务使用统一调用方式，Rockchip `IPreproc` 和 HiSilicon `rga_lib` 风格实现隔离在芯片后端。

### 必须补齐的审计

- 构建入口、SDK、工具链、子模块、动态依赖、安装路径和版本注入方式。
- 模型、标签、配置、运行库、实际设备加载路径和 SHA-256 清单。
- DMS 完整调用链：输入、帧适配、预处理、推理、后处理、跨帧状态、回调和资源释放。
- 日志、图片保存、性能统计、版本诊断、配置和错误处理等横切能力现状矩阵。
- `cnn_proc.cpp`、`dsmk_proc.cpp` 或两端等价大文件的函数级职责、共享状态、线程、平台依赖和候选模块边界。
- `SetSourceData` 退役证据：声明、实现、导出符号、上层调用、示例/测试调用、替代入口和 ABI 责任。

### 已知差异和风险

- 两端外部 ABI 不同，结构体、虚类、`std::vector` 和跨库内存所有权都需要 ABI 探针和旧上层最小程序验证。
- Hi 与 RV 的交付库拆分不同，库名、导出符号、SONAME、依赖和加载顺序应按平台保持。
- 旧平台宏已经进入业务层，不能只靠集中宏定义解决，必须把平台 SDK 和媒体处理依赖收回到后端。
- 目标检测阈值、ROI、回调次数和顺序、结果合并、析构行为、动态分辨率处理等都是上层可观察行为，不能未经确认就合并。
- 模型和配置缺少完整哈希时，不能形成跨平台精度、性能或最终行为一致性结论。
