## 2. 日志统一与解耦要核查什么

第一阶段不先决定使用哪一个日志库，而是回答现状与兼容问题：

- 列出 Hi、RV 两端所有日志宏、封装函数、直接日志库调用和初始化入口；
- 记录日志级别、模块名、格式、时间戳、线程信息、输出目标、滚动策略和配置来源；
- 找出日志调用是否进入实时热路径，是否持锁、分配内存或同步写盘；
- 找出现有上层程序、测试脚本或现场工具是否依赖固定日志文本；
- 区分产品运行日志、算法诊断日志、性能统计和临时调试输出；
- 记录初始化失败、日志后端不可用和退出阶段的行为；
- 明确人脸、图片路径、设备标识等敏感信息的脱敏和开关要求。

第一阶段输出“日志现状矩阵”和保留/修改/删除清单。第二阶段再定义统一日志门面、后端适配和依赖归属。DMS 业务核心不得直接依赖具体板端日志库。

## 3. 图片保存能力要核查什么

图片保存不是推理和告警规则的一部分，应作为可关闭的诊断能力核查。两端逐项记录：

- 调用位置和触发条件：按帧、按告警、按错误、按采样还是人工开关；
- 保存对象：原图、裁剪图、眼部 ROI、中间结果或叠加标注图；
- 像素格式、颜色转换、编码格式、图像质量和文件扩展名；
- 目录来源、文件命名、覆盖策略、磁盘配额、保留周期和清理责任；
- 同步/异步写盘、队列上限、背压、丢弃策略和退出时的在途任务；
- 目录不可写、磁盘满、编码失败时是否影响主算法；
- 配置项、默认开关以及不同平台和 PC 的行为差异；
- 人脸数据访问权限、脱敏、客户数据留存和发布限制。

第一阶段必须确认保存失败不能改变 DMS 主流程结果；若旧实现会阻塞或改变业务行为，应登记为待修缺陷，而不是默认为统一后的兼容行为。

## 4. `SetSourceData` 的退役判定

项目目标是删除废弃的 `SetSourceData` 实现，不把它迁入新的公共核心。删除前需要形成可审计证据：

1. 在两个固定源码 commit、上层应用、示例程序、测试和脚本中搜索声明、实现、导出符号与调用点；
2. 对照设备实际加载库的导出符号，确认它是否属于对外 ABI；
3. 确认 `MediaApiFrameSource` 或目标入口覆盖其仍有效的输入场景；
4. 记录物理地址、虚拟地址、像素格式、所有权、同步和 IVE/CPU 路径差异；
5. 由上层应用负责人确认没有仍在使用的调用者；
6. 给出删除验证：旧入口不再编译进新实现，主入口回归通过，符号检查结果符合兼容决策。

如果仍有调用者或既有二进制必须依赖该符号，第一阶段应把它标为“待退役兼容入口”，第二阶段设计最薄适配和明确移除版本；不能把旧实现复制进业务核心，也不能在没有证据时直接删掉导致 ABI 破坏。

## 5. 打破两文件模式的职责盘点

第一阶段先把 `cnn_proc.cpp` 和 `dsmk_proc.cpp` 中的代码按职责归类，而不是按文件名整体迁移。至少建立以下清单：

| 职责类别 | 需要记录的内容 | 候选去向（第二阶段确认） |
| --- | --- | --- |
| 生命周期与编排 | 初始化、启停、送帧、退出、错误状态 | runtime/orchestrator |
| 帧与内存适配 | 像素格式、stride、地址、所有权、缓存 | platform/frame adapter |
| 预处理与推理 | resize、crop、tensor、模型会话 | inference backend |
| 单帧结果解析 | 关键点、检测框、姿态、置信度 | perception/postprocess |
| 跨帧状态与告警 | 计时、滤波、状态机、告警规则 | behavior/decision modules |
| DSM 子功能 | 疲劳、分神、打电话/抽烟等 | 独立业务模块 |
| 配置 | 解析、默认值、校验、热更新 | configuration |
| 回调与兼容 | 旧 API、结构体、ybus/回调适配 | platform compatibility |
| 横切能力 | 日志、图片保存、性能统计、版本信息 | diagnostics/observability |
| 通用底层能力 | 不含 DMS 规则且有实际复用方的能力 | `algo-base` 候选 |

对每个函数和共享状态记录：输入输出、调用者、被调用者、所有权、线程、锁、静态/全局状态、配置依赖、平台宏、失败路径和可测试边界。函数没有完成归类时，不进入迁移任务。

第一阶段输出的是“现有职责—候选模块”映射。模块接口、目录结构和类设计在第二阶段评审通过后确定，避免把旧两文件机械切成多个仍然互相耦合的新文件。
