# DMS 平台统一：已确认的范围和约束

> 状态：草稿
> 基线日期：2026-08-07
> 维护入口：[DMS 运行时统一](../README.md)
> 关联代码仓库：`dms-deploy`、`algo-base`、Hi3519DV500 旧实现、RV1126B 旧实现

本文汇总截至 2026-08-07 已确认的要求。代码核查结果和工作计划见 [DMS 平台统一核查](./2026-08-07-dms-platform-unification-audit.md)。

## 1. 本次要完成什么

把 Hi3519DV500 和 RV1126B 中各自维护的 DMS 代码合并成一套业务实现，并支持：

- Hi3519DV500 板端；
- RV1126B 板端；
- x86_64 PC 离线运行。

DMS 业务代码放在 `dms-deploy`，DMS 实际依赖且适合复用的底层能力放在 `algo-base`。两个仓库分别管理版本，`dms-deploy` 的每个发布版本要固定对应的 `algo-base` tag 或 commit，并且能够单独克隆和编译。

这次不迁移 BSD、VMS、ADAS 和 CameraDeflection，也不使用 `board_deploy`。设计时要保证以后能增加其他业务，但不能为了可能的复用提前搬入这些业务的代码或建立没有实际调用方的公共模块。

### 本次代码治理目标

统一不是把两套旧目录合并到一起，还要完成以下治理：

- 日志入口统一并与 DMS 业务逻辑解耦，平台日志库限制在适配层；
- 图片保存从推理和告警流程中拆出，成为可关闭、失败不影响主流程的诊断模块；
- 清理已经证明无调用者且不承担兼容责任的废弃代码，包括 `SetSourceData` 实现；
- 打破 `cnn_proc.cpp`、`dsmk_proc.cpp` 承载大部分职责的两文件模式，按生命周期、帧适配、推理、单帧结果、跨帧判决、DSM 子功能、配置、兼容和诊断形成可测试边界；
- 每项删除和拆分都建立旧行为基线、替代路径、验证方法和回滚依据。

## 3. 兼容要求

上层应用暂时不改，因此 Hi3519DV500 和 RV1126B 各自现有的以下内容都要保持兼容：

- 公共 API 和头文件；
- C++ ABI；
- 库名、SONAME、软链接和依赖关系；
- 配置文件格式、已有字段及其含义；
- 模型和配置的部署路径；
- 初始化、启停、送帧、回调和释放时序；
- 告警结果、线程行为和错误处理。

两个平台的现有接口并不完全相同。统一的是内部业务实现，不要求把两套外部头文件改成一套。兼容基线包括：

- Hi3519DV500：`algo/dsm/src/dsm_proc/dsm_proc_interface.h`
- RV1126B：`sdk_rv1126b/hq/include/ai/bsd_dsm/dsm_proc_interface.h`

现有 DMS 交付库为：

| 平台 | 库 |
|---|---|
| Hi3519DV500 | `libhq_dsm_lib.so`、`libhq_dsm_proc.so` |

兼容要求不等于永久保留所有历史实现。`SetSourceData` 已列为废弃代码删除候选：第一阶段必须确认其上层调用、导出符号和替代入口；确认无有效调用者且不承担既有二进制兼容责任后，删除实现和新架构中的对应路径。若仍有兼容责任，则只保留有明确退役版本的最薄适配，不把旧实现迁入公共核心。
| RV1126B | `libhq_dsm_proc.so` |

PC 离线功能可以使用单独的运行入口和后端，但不能借此改变板端接口和配置格式。

## 4. `algo-base` 的范围

是否进入 `algo-base`，要从 DMS 的真实调用链判断。候选代码至少满足以下条件：

- DMS 确实在使用；
- 不包含 DMS 告警规则、状态机等业务逻辑；
- 不依赖 `dms-deploy`；
- 平台 SDK 依赖可以限制在具体后端内；
- 模块有明确接口、测试方法和发布责任。

本次不把两个旧仓库的 `base/common` 或 `common_core` 整体搬入 `algo-base`。同名文件先比较输入输出、内存所有权、线程行为和调用方，再决定合并；名称不同但职责相同的实现也要一起比较。

`dms-deploy` 可以源码依赖 `algo-base`，但构建时必须固定 commit。`algo-base` 修改后是否需要重发 DMS，不能只看 DMS 源码有没有变化，还要检查 ABI、重新构建反向依赖并执行相关回归。

## 5. 平台差异怎么处理

代码对比中发现差异时按以下顺序处理：

1. 硬件、SDK、模型格式或媒体内存造成的差异留在平台后端。
2. 已确认的缺陷修复合并到公共实现，并在两个板端和 PC 回归。
3. 产品规则或客户需求造成的差异保留在业务配置或兼容层，不能伪装成平台差异。
4. 暂时无法判断的差异先记录源码位置、运行影响和所需确认人，不擅自选择任一平台行为。

第 3、4 类差异的最终确认人尚未指定。进入相应代码迁移前，需要由 DMS 算法负责人和产品负责人确认；涉及帧、SDK 或板端资源时，再由对应板端负责人确认。

## 6. 构建、安装和版本追溯

安装根目录可以配置。计划把不同平台的构建结果集中保存，但目录至少要区分算法、平台、架构、版本和构建类型，避免同名 `.so` 相互覆盖。

归档目录和目标机部署目录是两件事：前者用于查找和追溯版本，后者继续满足上层应用和动态加载器的现有路径要求。

每次发布至少记录：

- `dms-deploy` commit；
- `algo-base` tag 或 commit；
- SDK、工具链和子模块版本；
- 模型与标签文件版本或摘要；
- 配置摘要；
- 平台、架构、构建类型和关键构建选项；
- 产物摘要及生成时间。

## 7. 验收范围

现在不要求先提供完整回归资料，设计方案需要给出可执行的验收办法。正式迁移前仍要从现网素材中建立一套可重复运行的基线，否则无法判断重构是否改变行为。

验收至少覆盖：

- 原头文件配合新库的编译、链接和最小运行测试；
- 导出符号、结构体布局、枚举值、SONAME 和动态依赖；
- 输入格式、预处理、推理输出、后处理、跨帧状态和最终告警的分段对比；
- 初始化、重复初始化、启停与送帧并发、回调重入、队列满和退出；
- 模型缺失、设备初始化失败和无效配置；
- FPS、时延、内存、启动时间和长时间运行；
- Hi3519DV500、RV1126B 和 PC 的结果差异及允许范围。

PC 主要用于快速回归公共业务逻辑。只有模型、预处理和输入语义与板端一致时，PC 结果才可以用来判断板端精度；板端的零拷贝、缓存、SDK 和资源生命周期仍需在真机验证。
