## 已经确认的问题

### 两个平台的外部 ABI 不同

已比较以下接口：

- Hi：`algo/dsm/src/dsm_proc/dsm_proc_interface.h`
- RV：SDK 子模块中的 `hq/include/ai/bsd_dsm/dsm_proc_interface.h`

RV 的 `DsmAlgoConfig` 比海思多 `enableDsmState`，结构体布局因此不同。接口中还有 `std::vector`、虚类、带构造函数的结构体以及跨动态库传递的内存，这些都会受到编译器选项和 C++ ABI 的影响。

所以不能用一份新公共头直接替换两边现有头文件。更稳妥的做法是合并内部 DMS 核心，在外层保留 Hi 和 RV 各自的兼容实现。最终设计仍要用 ABI 探针和旧上层程序验证。

### 交付库的拆分方式不同

Hi DMS 交付 `libhq_dsm_lib.so` 和 `libhq_dsm_proc.so`，RV DMS 只交付 `libhq_dsm_proc.so`。源码可以共用，库名、导出符号、SONAME、依赖和加载顺序仍需保持平台原状。

### 两个基础目录不能按文件名直接合并

Hi 的 `base/common` 主要包含 `blur_det`、`infer_core_lib`、`mem_encryption`、`object_det`、`spdlog` 和第三方依赖。RV 的 `common_core` 还有 `IPreproc`、`common`、`hqinit`、`sorttracker`、`utils` 和 `video_source`，推理接口也不同。

文件同名不代表输入输出和生命周期相同，文件不同名也可能做同一件事。后续比较要从 DMS 的调用方出发，逐项核对数据、线程、内存和错误处理。

### 旧平台宏已经进入业务层

现有代码仍使用 `HQ_FLAG_HI3519D`、`HQ_FLAG_HI3519DV500`、`HQ_FLAG_RV1126`、`HQ_FLAG_RK1808` 和 `USE_HISI` 等条件。RV 的 BSD/DMS CMake 还会定义 `HQ_FLAG_HI3519D`，视频源中也保留旧平台分支。

这不只是宏名称混乱。平台 SDK 和媒体处理已经穿过多层代码。重构要把依赖收回到平台后端，并从业务核心删除无关的平台条件；把宏集中到一个头文件解决不了这个问题。

### 安装和版本信息来自多处

Hi 同时使用模块内 `CMAKE_INSTALL_PREFIX`、生产脚本变量和源码树安装目录。RV 还使用 `RV1126BINSTALLPREFIX`、SDK 路径和版本注入函数。

统一的归档位置应按平台和版本保存产物，目标机安装仍要兼容原路径。两种用途不能共用一个扁平目录，否则同名库会覆盖，也很难确认设备实际加载了哪一份。

## 第一阶段仍缺失的代码治理核查

主调用链核对不能代替文件和函数职责盘点。以下内容当前都是进入第二阶段前必须补齐的阻塞项：

- 日志：两端宏、封装、后端、配置、输出格式、性能和现有解析依赖；
- 图片保存：触发条件、保存内容、路径命名、同步/异步 IO、频控、磁盘失败和数据留存；
- 废弃路径：`SetSourceData` 的声明、实现、导出符号、调用者、替代入口和删除条件；
- 两文件模式：`cnn_proc.cpp`、`dsmk_proc.cpp` 中每个函数、共享状态、线程和平台依赖的职责归类；
- 其他横切能力：配置、性能统计、版本诊断、错误处理和临时调试代码的去留。

当前可访问工作区不包含两个固定 commit 下的上述目标源码，因此还不能给出函数级结论。补充核查必须使用固定 commit，而不是当前工作区或口头记忆。

第一阶段只形成现状、证据、去留建议和候选职责边界。统一日志接口、图片诊断接口、模块目录和类设计属于第二阶段；删除 `SetSourceData`、拆分两文件及迁移实现属于第四阶段。这样既不把设计决定伪装成代码事实，也避免在实施阶段重新猜测范围。

详细检查项、证据要求和负责人表见 [DMS 第一阶段代码治理核查清单](./2026-08-18-dms-phase-1-code-governance-inventory.md)。

## 设计时还要补齐什么

### 1. 先定义内部边界

建议把代码分成四类：

| 代码 | 放置位置 | 说明 |
|---|---|---|
| DMS 状态机、过滤和告警规则 | `dms-deploy` 的业务核心 | 三个平台尽量共用，不直接调用板端 SDK |
| Hi/RV/PC 推理、预处理、帧和设备实现 | 平台后端 | 允许使用各自 SDK 和模型格式 |
| 旧 API、库拆分、ybus/回调适配 | 平台兼容层 | 对上层保持现有行为 |
| 已被 DMS 调用且不含业务规则的通用能力 | `algo-base` | 由调用链和测试证明可以独立发布 |

依赖方向为 `dms-deploy -> algo-base`。`algo-base` 不引用 DMS 类型，业务公共头也不放进 `algo-base`。以后接入 BSD、VMS、ADAS 或 CameraDeflection 时沿用同样的后端接口和构建约定，但等到出现真实调用方再扩大公共层。

### 2. 补齐输入到输出的语义

两个平台要按同一条链比较：

```text
外部输入 → 帧适配与所有权 → 预处理 → 推理 → 后处理
        → 跨帧状态与告警规则 → 外部输出 → 资源释放
```

每一步都要核对像素格式、通道顺序、数值范围、stride、裁剪和缩放取整、张量布局、量化、坐标系、时间戳、线程、队列、丢帧和释放方。出现结果差异时先定位最早不同的中间结果，再判断是硬件限制、模型差异、业务规则还是历史缺陷。

### 3. 分别验证两套 ABI

Hi 和 RV 各建一份兼容检查，不要求跨架构产生相同二进制。检查内容包括：

- `sizeof`、`alignof`、字段偏移和枚举值；
- 导出符号、SONAME、NEEDED、RPATH/RUNPATH；
- 编译器、目标架构、C++ 标准、libstdc++ ABI、RTTI、异常和符号可见性；
- 对象在哪个库创建和销毁；
- 原头文件配合新库的编译、链接与运行。

### 4. 说明 PC 能验证什么

PC 用于快速运行公共业务逻辑和离线回归。若 PC 与板端使用不同模型、预处理或输入格式，结果只能说明相应公共代码没有变化，不能证明板端精度相同。板端的媒体帧、零拷贝、缓存和 SDK 生命周期继续在真机测试。

### 5. 把失败和并发纳入设计

现有接口包含异步初始化、Enable/Uninit、回调、引用计数和裸指针。测试需要覆盖重复初始化、初始化到一半失败、启停和送帧并发、回调重入、队列满、在途帧退出、模型缺失、设备失败、内存泄漏、死锁和退出超时。

### 6. 让运行版本可查

设备日志或诊断接口应能查到 DMS、`algo-base`、模型、平台后端、配置路径和实际加载库的版本。发布记录还要包含 SDK、工具链、构建选项和文件摘要。新增日志时需确认不会影响现有日志解析程序。

模型、工具链和第三方库还要记录来源和补丁。涉及人脸数据的回归集应限制访问，并明确模型或配置加密时的密钥边界。

## 对原计划的调整

原计划先比较基础库，再比较业务代码。这样容易在理解调用链之前决定什么属于 `algo-base`。新的顺序从 DMS 的完整运行路径开始，再抽取公共能力。

### 第一步：固定可复现基线

除源码 commit 外，收集公共头、当前交付 `.so`、模型、配置、SDK、工具链、构建参数和最小上层调用程序。缺少的材料明确标为待补，不用现有目录或文件时间代替。

进入下一步前，任一测试结果都应能对应到具体源码、模型、配置和构建环境。

### 第二步：建立原行为测试

选择能够覆盖初始化、正常检测、状态切换、异常输入和退出的图片或视频。在两个板端记录关键中间结果、最终告警、性能和资源使用。暂时无法自动判断的结果先保存为特征化测试，由算法负责人确认后再作为预期值。

### 第三步：比较完整调用链

按输入、预处理、推理、后处理、状态、输出和释放逐段比较 Hi 与 RV。每项差异记录源码位置、运行影响、原因判断和确认人。原因不清楚时不把任一平台实现直接当作公共版本。

### 第四步：确定模块归属和接口

根据调用链画出 DMS 核心、三个平台后端、两套兼容层和 `algo-base` 的依赖关系。逐个审查准备迁入 `algo-base` 的模块，确认它有实际调用方、不包含 DMS 规则，并能独立测试和发版。

同时用 BSD、VMS、ADAS 或 CameraDeflection 的一个真实调用片段检查接口是否过度绑定 DMS。这里只做接口检查，不迁移它们的代码，也不因此增加公共功能。

### 第五步：确定兼容和发布方式

设计文档要列出两个平台的 API/ABI 保持方法、库依赖图、配置处理、归档目录、目标机部署目录、版本清单和回滚方法。用旧上层最小程序验证无需改代码即可运行。

### 第六步：小步迁移

优先迁移一个输入到输出可独立验证的 DMS 切片。每一步同时运行旧实现和新实现，比较中间结果、最终告警和资源使用；通过后再删除对应旧路径。不要先整体搬目录再集中排错。

### 第七步：完整验收和切换

在 Hi3519DV500、RV1126B 和 PC 执行功能、ABI、异常、并发、性能和长时间测试。板端结果达到既定范围后再切换默认实现。旧版库、模型、配置和安装脚本保留到回滚窗口结束。

## 还需人工确认的决定

以下问题会直接影响代码，不能由现有目录结构代替决定：

- 两个平台业务行为冲突时，谁代表算法和产品确认预期结果；
- 哪些数值差异、告警时间差异和性能变化可以接受；
- 某项产品差异通过配置保留，还是在本次统一；
- `algo-base` 变更在什么条件下允许独立发布；
- 设备需要提供哪种运行版本查询方式。

在这些问题影响到具体迁移步骤之前确认即可，不需要阻塞现阶段的基线收集和调用链对比。

## 结论

目前最合适的候选结构是“公共 DMS 核心 + Hi/RV/PC 平台后端 + Hi/RV 外部兼容层 + 较薄的 `algo-base`”。它能直接解决两套业务代码重复维护的问题，同时保留现有上层接口。后续代码对比如果证明平台差异已经深入状态机或模型规则，需要重新划分公共核心，不能为了目录统一强行合并。
