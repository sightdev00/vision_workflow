# 人-智能体协作工作流模型

## 1. 目的

本文定义仓库中长期问题、人-智能体协作工作流、可复用能力和有限执行会话之间的稳定关系。
目标不是让智能体 自己判断并宣布完成，而是把人的领域知识、系统工程经验、约束和验收判断转换为可执行、可验证、可恢复的工程流程。

本模型的基本闭环是：

```text
人
│  原因 / 目标 / 判断
▼
工作流意图
▼
工作流模式
▼
能力契约
▼
技能与工具
▼
智能体执行
▼
外部证据
▼
人工判断与状态转换
```

### 1.1 三级演进目标

当前模型不直接从单一项目跳到通用框架，而按三个层次演进：

```text
真实问题实例
→ 领域可复用工作流
→ 通用公开工作流库
```

#### P-001真实问题实例

P-001以RV1126B（历史别名RV1126BP）和HiSilicon DMS代码统一与重构为真实验证场。它负责暴露：

- 大量人工经验如何进入工作流；
- 不完整源码和冲突基线如何处理；
- 平台差异、兼容责任和重构目标如何共同约束设计；
- 审计、设计、承诺、实现、验证和留存能否形成完整闭环；
- 哪些工作流机制只是P-001特例，哪些具有算法工程复用价值。

P-001的工程完成条件仍由其代码、制品和外部验证决定，不能用“工作流已经形成”替代。

#### 算法工程可复用工作流

第二层从真实实例中提取算法软件工程领域的模式，覆盖源码基线、构建与运行制品、调用链、平台边界、统一范围、架构与接口、迁移、跨平台验证和知识留存。

该层可以保留算法工程语义，但不得绑定具体业务名称、芯片、目录、提交或会话编号。人工经验必须成为可追溯的一等制品，并能够影响分析、设计、决策和验收。

进入本层的最低证据是：

- P-001至少贯通审计、设计和人工承诺；
- 候选模式明确区分实例参数、领域规则和通用控制机制；
- 在第二个独立算法问题中无需复制P-001专用逻辑即可实例化和执行。

#### 通用公开工作流库

第三层把领域模板与通用引擎分离。通用引擎只负责状态、制品、依赖、影响、门禁、验证、恢复和晋升，不内置DMS或算法工程判断；算法工程工作流作为领域模板存在。

公开库还必须具备版本化结构定义、模板初始化、兼容升级、扩展接口、自动检查、测试、示例、文档、许可证和发布治理。进入本层必须有跨实例复用证据，而不是仅依据抽象设计判断可复用。

三个层次之间使用人工晋升门禁，不自动提升：

```text
实例事实 ≠ 领域模式
领域模式 ≠ 通用机制
一次成功 ≠ 可公开复用
```

## 2. 核心原则

### 2.1 人保留目标、责任和最终判断

人主要负责：

- 判断为什么值得做以及后果是否可接受；
- 定义问题、范围、约束和验收标准；
- 确认高风险边界、行为差异和承诺门；
- 判断现有证据是否充分；
- 决定接受、拒绝、回退、暂停或重新定义问题。

智能体主要负责：

- 搜索、分析、实现、工具调用和迭代；
- 执行常规验证并收集证据；
- 识别缺失前置条件、失败模式和能力缺口；
- 提出工作流状态转换建议；
- 将可复用经验沉淀为候选工作流模式或能力改进。

智能体不得同时作为实现者和最终验收者。

### 2.2 验证不等于判断

外部判定机制可以回答测试是否通过、误差是多少、延迟是否越界、构建是否成功。
人工判断还必须回答测试是否充分、阈值是否合理、风险是否可接受以及是否遗漏了系统性失败模式。

### 2.3 工作流模式与能力分离

- 工作流模式描述策略：调用顺序、分支、停止条件、人工门禁和失败恢复。
- 能力描述机制：职责、输入、输出、前置条件、后置条件、失败模式和验证方法。
- 技能描述智能体如何调用具体脚本、工具、环境和恢复过程。

工作流应保持较薄，能力应成为可独立维护和回归验证的长期资产。

### 2.4 会话是有限执行上下文

问题是长期语义边界；工作流实例是问题的可执行控制结构；会话是某个工作流节点的一次有限执行尝试。

```text
问题 1 ── N 工作流实例
工作流实例 1 ── N 工作流节点
工作流节点 1 ── N 执行尝试
执行尝试 1 ── 1 会话记录
```

会话关闭只表示该执行上下文已经封存，不表示节点、工作流或问题已经完成。
已关闭会话不得改回活动状态；继续、重试或恢复必须创建新会话并保留父会话关系。

## 3. 核心对象

### 3.1 问题

长期语义目标，保存目的、范围、责任边界、稳定约束、主要风险和最终关闭条件。

### 3.2 工作流实例

针对一个问题的具体执行控制对象，至少包含：

- `workflow_id`；
- `problem_id`；
- 工作流模式及版本；
- 全局状态；
- 当前可执行节点；
- 全局输入和验收条件；
- 节点图；
- 决策和证据索引。

### 3.3 工作流模式

跨问题复用的控制流知识，定义节点类别、依赖、分支、门禁、失败路径和结束条件。
模式不是某个项目的会话列表，也不绑定具体芯片、模型或文件路径。

### 3.4 工作流节点

工作流中的可判断状态单元，至少包含：

- 唯一标识和职责；
- 前置节点；
- 所需能力；
- 输入和预期产物；
- 外部判定机制和验收标准；
- 智能体权限；
- 人工门禁；
- 失败与恢复路径；
- 当前状态；
- 执行尝试列表。

### 3.5 能力

系统能够可靠完成什么的稳定语义契约，至少包含：

- 职责；
- 输入和输出；
- 前置条件和后置条件；
- 不变量；
- 失败分类；
- 验证方法；
- 恢复建议；
- 扩展点和版本。

### 3.6 技能

能力面向智能体的具体实现载体，包括工具绑定、命令、脚本、环境知识、操作说明和恢复过程。
技能可以实现一个能力，也可以组合多个较低层能力。

### 3.7 会话与执行尝试

会话记录一次有限的人-智能体协作上下文。执行尝试把会话绑定到工作流节点，并记录：

- 节点标识；
- 尝试序号；
- 父会话；
- 智能体和接口；
- 基线提交；
- 输入快照；
- 产物和证据；
- 转换建议；
- 未解决事项。

### 3.8 证据

支持事实、验证结果或状态转换的可追溯对象。证据必须尽可能绑定命令、输入、输出、日志、制品、源码提交、平台和时间。

### 3.9 决策

由明确责任人基于证据作出的判断，至少包含决策者、可选结果、实际决定、理由、证据引用、时间和产生的状态转换。

### 3.10 人工门禁

要求人工承担责任的决策点。门禁必须声明：

- `gate_id`；
- 决策责任人；
- 必需证据；
- 允许的决策；
- 是否阻止自动推进；
- 决策记录路径。

## 4. 状态机

### 4.1 工作流实例状态

```text
draft → active → awaiting-human → verifying → completed
                  │                 │
                  ├──────────────→ blocked
                  └──────────────→ cancelled
```

`completed`只允许在所有必要节点均已接受且最终人工门禁通过后进入。

### 4.2 工作流节点状态

允许状态：

```text
planned
ready
active
awaiting-human
verifying
accepted
rejected
blocked
superseded
```

允许转换：

```text
planned → ready
ready → active
active → awaiting-human | verifying | blocked
awaiting-human → active | verifying | rejected | blocked
verifying → accepted | rejected | active | blocked
rejected → ready | superseded
blocked → ready | superseded
```

`accepted`和`superseded`是终态。若已接受结论被新反证推翻，应创建替代节点或新工作流修订，不直接改写历史状态。

### 4.3 会话状态

```text
active → closed
active → abandoned
```

会话状态不参与工作流完成判定。

## 5. 状态转换规则

- 智能体可以提出转换建议，但不能自行通过要求人工判断的门禁。
- 进入`active`前必须满足前置节点和输入条件。
- 进入`verifying`前必须存在候选产物或结论以及可执行外部判定机制。
- 进入`accepted`必须存在验证证据；节点声明人工门禁时还必须存在有效决策记录。
- 缺少外部环境、硬件、权限或权威输入时进入`blocked`，不得默认为通过。
- 发现前提错误时可以回到`active`或`ready`，并保留失败证据。
- 工作流实例的状态由节点状态和人工决策派生，不由会话编号推断。

## 6. 人工门禁分类

### 6.1 问题门禁

确认问题目的、范围、非目标和责任人。

### 6.2 设计承诺门

确认公共层与平台层边界、接口、ABI、迁移顺序、行为差异、验收标准和回滚路径。

### 6.3 高风险执行门

确认删除、不可逆迁移、外部发布、生产环境修改或其他高影响动作。

### 6.4 验收门

确认外部证据充分、差异在允许范围内、剩余风险已记录并决定是否接受。

## 7. 证据和外部判定机制

每个节点应明确外部判定机制类型：

- 源码和Git基线；
- 构建系统；
- 单元或集成测试；
- 固定输入输出；
- PC基线；
- 板端日志；
- 性能、精度和稳定性数据；
- 人工审查或业务判断。

同一智能体的自我评价不能作为唯一外部判定机制。

## 8. 失败与恢复

工作流模式必须为可预期失败定义路径：

```text
前置条件缺失 → blocked
验证失败 → rejected或active
发现错误问题定义 → awaiting-human
能力缺失 → 记录能力缺口并决定扩展能力或使用局部实现
会话上下文耗尽 → 关闭当前会话并创建同节点的新尝试
出现关键反证 → 保留证据并回到允许的上游节点
```

## 9. 活动制品协作与稳定知识晋升

完整制品模型和状态契约见`docs/2026-08-20-workflow-artifact-system-design.md`。当前系统采用以下机制：

- 人可以直接编辑仓库内Markdown制品，智能体继续工作前必须重新读取磁盘；
- `WORKFLOW.json`显式声明节点的活动制品、依赖、完成条件、影响关系、外部判定机制和晋升目标；
- `status`和`instructions`提供稳定的文本及JSON读取接口，避免智能体从聊天上下文猜测当前状态；
- 人工经验、人工决定、智能体建议、外部证据和权威控制状态分别保存，不混为同一结论；
- `review`只检查结构，`verify`分别检查完整性、正确性和一致性，外部证据及人工判断仍是接受节点的必要条件；
- `reconcile`用于分析人工编辑对多个制品的前向和反向影响，但只有用户批准后才能写入；
- `retain`把已接受的活动知识晋升到问题记录、正式文档、清单或验证制品；会话关闭只负责封存上下文。

本模型明确拒绝“文件存在即完成”“任务复选框完成即接受”“通用`--yes`绕过人工门禁”和“智能体自评代替外部验证”等语义。

## 10. 系统学习闭环

一次工作流结束后必须区分：

- 仅属于当前实例的特殊处理；
- 可进入工作流模式的控制知识；
- 可进入能力契约的稳定职责；
- 应更新技能的工具或环境知识；
- 不可形式化、仍需人工判断的风险。

候选模式或能力改进必须经过独立验证和回归测试后才能成为稳定资产。

## 11. 度量

至少记录：

- 节点和工作流最终结果；
- 人工介入次数及原因；
- 智能体自主执行链长度；
- 失败、重试和恢复次数；
- 证据完整度；
- 能力和工作流模式复用情况；
- 新增或修正的能力缺口；
- 未被工作流覆盖、依赖人工判断的异常。

模型版本不是唯一变量。工作流模式、能力成熟度、智能体权限、人工介入和结果质量共同构成系统能力。

## 12. 与仓库资产的对应关系

| 对象 | 当前存放位置 |
| --- | --- |
| 问题 | `.problems/<problem-id>/README.md` |
| 工作流实例 | `.problems/<problem-id>/WORKFLOW.json` |
| 会话路线投影 | `.problems/<problem-id>/SESSION-PLAN.md` |
| 会话执行记录 | `.problems/<problem-id>/sessions/*.md` |
| 稳定工作流模式 | `docs/`中的正式设计文档，后续可独立建立模式清单 |
| 能力契约 | 后续按实际复用需求建立，不预建空目录 |
| 技能和工具 | 智能体环境或仓库`tools/`中的具体实现 |
| 证据和决策 | 问题记录、会话记录、测试报告、日志和制品路径 |

`SESSION-PLAN.md`只作为面向人的路线投影，不是工作流状态的权威来源。
