# 工作流制品系统设计

## 1. 目的

本文定义当前问题/工作流/会话系统内部的制品模型。目标是让人的经验补充、人工决定、智能体执行、外部证据、状态转换和稳定知识留存形成同一个可计算系统，而不是依赖聊天记忆、会话编号或手工修改状态字段。

### 1.1 系统建设目标

制品系统同时服务三个不同层次，但不得混淆它们的权威范围：

| 层次 | 主要对象 | 当前责任 | 形成条件 |
| --- | --- | --- | --- |
| P-001实例 | 真实源码、经验、证据、决定和验证 | 验证工作流能否支撑一次复杂算法统一与重构 | P-001节点按工程证据推进 |
| 算法工作流模板 | 算法工程节点类型和制品契约 | 复用跨平台审计、重构、迁移和验证方法 | 至少两个独立算法实例验证 |
| 通用公开库 | 领域无关引擎、结构定义和扩展接口 | 提供可安装、可升级、可测试的工作流基础设施 | 领域模板与核心引擎成功解耦 |

系统资产相应分为：

```text
通用引擎
├─ 状态与转换
├─ 制品契约与派生
├─ 依赖和影响传播
├─ 人工门禁
├─ 验证、恢复与晋升
└─ 版本及扩展机制

领域模板
└─ 算法工程统一与重构工作流

项目实例
└─ P-001 RV1126B（历史别名RV1126BP）/HiSilicon DMS统一与重构
```

当前仓库首先验证项目实例和算法模板候选。通用公开库是经过复用验证后的独立成果，不作为当前P-001节点的自动附带产物。

### 1.2 人工经验的系统位置

复杂重构中的人工经验至少分为：

- 领域经验：业务规则、状态语义和结果解释；
- 平台经验：芯片SDK、媒体、内存、缓存和生命周期约束；
- 历史经验：旧实现形成原因和已知失败方案；
- 兼容经验：上层应用、ABI、配置和交付依赖；
- 重构经验：职责问题、目标边界和可接受变化；
- 验证经验：高风险输入、设备差异和故障场景。

经验条目至少应记录适用范围、陈述、来源、条件、证据状态、影响对象、冲突项、处理状态和晋升目标。经验进入系统后的处理链为：

```text
人工补充
→ 结构化经验制品
→ 证据核查与状态分类
→ 影响传播
→ 人工采纳、拒绝或延期
→ 设计约束或验收条件
→ 外部验证
→ 稳定知识或领域模板候选
```

## 2. 四层系统模型

### 2.1 稳定知识层

保存已经成立并需要长期维护的事实和规则：

- `README.md`和`AGENTS.md`；
- `docs/`中的正式设计；
- `manifests/`中的来源、迁移和版本清单；
- 已接受节点的结论和证据指针；
- 外部验证报告和可追溯制品。

稳定知识只能由已经验证并经人工接受的活动制品晋升而来。

### 2.2 活动制品层

保存当前问题中仍可修改、尚未成为稳定事实的内容：

- 当前问题记录；
- `WORKFLOW.json`；
- 活动会话；
- 审计结论、候选设计和验证报告；
- 人工经验卡和人工决定卡；
- 稳定知识晋升候选。

活动制品允许人直接编辑。任何编辑发生后，智能体必须重新读取磁盘并重新计算依赖、影响和完成状态。

### 2.3 控制节点层

工作流节点负责：

- 工程阶段和权限；
- 节点之间的前置依赖；
- 人工门禁；
- 可执行、阻塞、验证和接受状态；
- 会话执行尝试。

节点状态不能从文件存在或任务复选框数量直接推出。制品图只回答上下文和结构是否具备，节点接受仍需要外部证据和人工判断。

### 2.4 人工判断层

人工判断负责：

- 经验信息是否表达准确；
- 候选方案和风险是否可接受；
- 外部证据是否充分；
- 是否接受、拒绝、延期或替代节点；
- 哪些活动知识可以晋升为稳定知识。

智能体可以形成建议和证据索引，但不能代替人工勾选决定或完成最终门禁。

## 3. 制品契约

每个进入`ready`的节点必须先声明自己的制品契约。契约至少包含：

```text
id
title
kind
lifecycle
path 或 path_source
required
requires
completion
impacts
rules
oracle
targets
```

### 3.1 制品种类

- `stable-input`：稳定输入，例如源码基线清单；
- `human-experience`：人的经验信息，不自动等于事实；
- `analysis`：审计、推理或设计结论；
- `evidence`：命令、源码、日志、测试和制品证据；
- `human-decision`：需要责任人确认的决定；
- `verification`：完整性、正确性和一致性报告；
- `promotion`：活动知识到稳定知识的晋升计划。

### 3.2 完成条件

当前支持：

- `file-nonempty`：文件存在且非空；
- `section-present`：指定章节存在；
- `section-nonempty`：指定章节存在且有内容；
- `cards-confirmed`：指定人工卡片存在、已勾选且无占位符；
- `node-accepted`：节点已通过正式接受门禁。

完成条件只证明契约中的结构事实。验证制品即使结构完整，状态仍显示为`review-required`，不能把“有验证报告”解释成“验证结论已被接受”。

## 4. 制品依赖图

`requires`描述一个制品需要读取哪些上游制品，`impacts`描述本制品变化时必须重新审查哪些下游制品。

两者用途不同：

- `requires`用于计算`ready`或`blocked`；
- `impacts`用于人工编辑后的影响传播；
- 反向影响由所有`impacts`自动建立；
- 制品可以在任意时间修改，依赖顺序不是单向编辑限制；
- 下游文件提前存在时，如果上游不满足，仍然是`blocked`，不能因文件存在跳过依赖。

## 5. 派生状态

工具每次运行时从`WORKFLOW.json`和磁盘重新派生：

```text
missing
blocked
ready
available
complete
confirmed
review-required
promotion-pending
```

权威关系为：

```text
磁盘事实 + 制品契约 → 制品状态
节点依赖 + 制品完整性 + 外部证据 + 人工决定 → 节点转换
所有必要节点接受 + 最终人工门禁 → 问题完成
```

不得把派生制品状态反向写成未经人工判断的节点接受状态。

## 6. 人工经验和人工决定

人的经验与决定必须分离：

- 经验回答“人知道或怀疑什么”；
- 证据回答“当前可直接验证什么”；
- 结论回答“证据支持什么”；
- 决定回答“责任人选择什么以及接受哪些风险”。

经验变化会影响结论和决定；证据变化会影响结论、决定和验证；决定变化必须反向显示其依赖的清单、经验、结论和证据。

## 7. 命令读取模型

### `status`

显示节点状态，同时显示必需制品完成比例、制品状态、阻塞原因和下一动作。未来节点若尚未声明制品契约，下一动作是`define-artifact-contract`。

### `instructions`

不再只输出节点文字说明，而是输出：

- 稳定知识层和活动制品层；
- 每个制品的实际路径；
- 依赖、状态、完成条件和规则；
- 当前可处理制品与阻塞制品；
- 节点外部判定机制和人工门禁。

### `review`

只检查人工卡片结构和必需决定完整性，不判断工程事实。

### `verify`

从制品图计算完整性；正确性始终要求外部判定机制和人工复核；一致性检查会话绑定和制品依赖。验证命令从不接受节点。

### `reconcile`

选择一个制品后，输出它的前向影响和反向依据。智能体必须重新读取相关路径，逐制品说明因果关系，并在得到人工批准后才写入。

### `retain`

从`promotion`制品读取来源、依赖和目标。只有节点已接受且晋升制品契约满足时，候选才变为可晋升；命令本身不写文件。

## 8. 状态门禁

### 进入`ready`

- 节点前置依赖已接受；
- 节点已经声明非空制品契约；
- 制品标识、依赖、影响、路径和完成类型通过`doctor`检查。

### 进入`accepted`

- 所有必需制品满足契约；
- 必需人工决定完整；
- 外部验证证据已经形成；
- 人工门禁记录位于仓库内；
- 接受操作仍由显式`transition`完成。

## 9. 活动知识晋升

晋升不是复制会话全文，而是逐项选择：

```text
活动制品
  ├─ 状态和证据指针 → 问题记录
  ├─ 已确认设计 → docs/
  ├─ 来源和版本 → manifests/
  ├─ 测试和日志 → 验证制品
  └─ 未证实经验、被拒绝方案 → 留在会话历史
```

`retain`和`close`必须分离：

- `retain`决定哪些知识进入稳定层；
- `close`只封存一次有限执行上下文；
- 会话关闭、Git提交和节点接受互不替代。

## 10. 当前P-001节点实例

`source-baseline-validation`包含：

```text
source-manifest
├─ baseline-findings
├─ baseline-evidence
│  ├─ baseline-decisions
│  └─ baseline-verification
├─ human-experience
│  └─ baseline-decisions
└─ baseline-retention
```

其中：

- 源码清单变化要求重新审查结论、证据、决定和验证；
- 人工决定依赖清单、经验、结论和证据；
- 验证报告结构完整后仍保持`review-required`；
- 稳定知识晋升在节点接受前保持`promotion-pending`。

## 11. 设计边界

当前明确不采用：

- 文件存在即完成；
- 复选框全部勾选即节点接受；
- 自动确认人工门禁；
- 智能体自评代替外部验证；
- 将所有问题强制套入固定的提案/规格/任务目录；
- 为尚未进入`ready`的未来节点预建大量空制品；
- 把聊天记录或智能体总结当成权威状态。

未来节点在真正准备执行时按实际职责声明制品契约，实现渐进式严格性，而不是预建空结构。
